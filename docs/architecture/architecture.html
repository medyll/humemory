Internal architecture / actual execution paths

What runs, what it reads,
and what it writes.

A technical description of humemory: entry points, process lifetimes, configuration, SQLite tables, ingestion, retrieval, scheduled cues, decay and cross-session proposals.

The numbered chapters below describe runtime operations. “Phase 5”, “Phase 6”, “Phase 7” and “Phase 8” in the project plans are development milestones; they are not stages that every request executes.

Three separate mechanisms. SQLite stores the data. FlexSearch provides lexical retrieval in each process. Optional ONNX embeddings provide a second retrieval and clustering path. A generative LLM is optional for session extraction; it is not involved in ordinary search.
01 / Topology

Execution map

The client starts hooks or an MCP process. The CLI and HTTP API open the same database through SQLiteStore. A maintenance pass consumes the disk queue. Decay and the dreamer are separate operations.

AI client ── Stop hook ──► queue files ── maintenance pass ──► SQLite AI client ◄─ SessionStart hook ◄── cues + intentions + scripts + memories AI client ◄─► MCP stdio process ◄─► SQLiteStore Browser ◄─► HTTP API (:3456) ◄─► SQLiteStore Developer ──► CLI ──► search / encode / decay / dream / scripts / intentions SQLiteStore ──► FlexSearch index in process memory SQLiteStore ──► memory_embeddings in the same SQLite file Semantic CLI / vector dreamer ──► local ONNX model + cosine calculations

02 / Deployment

Installation and process lifetimes

Working from this checkout

The backend requires Bun ≥ 1.3.14 because the store imports bun:sqlite. The package uses pnpm 10.33.2. The build compiles TypeScript into dist/, type-checks the React frontend and bundles it into public/app/.

pnpm install
pnpm build
pnpm cli doctor
pnpm start:api
# Open http://127.0.0.1:3456/app

pnpm cli … runs src/cli/index.ts with Bun. The installed humemory executable runs bin/humemory.js, which imports dist/cli/index.js. Auxiliary hook, API and maintenance scripts are separate entry points. The first store construction creates the database directory, tables and schema migrations.

Windows startup and watchdog

pnpm win:install
# Equivalent:
pwsh -File scripts/windows/install.ps1 -WatchdogMinutes 5

# Remove the startup registration and scheduled task:
pwsh -File scripts/windows/install.ps1 -Uninstall
  1. Installer creates a Startup shim.A generated humemory-api.vbs in the Windows Startup folder delegates to this checkout's scripts/windows/humemory-api.vbs.
  2. Installer registers a scheduled task.humemory-watchdog runs humemory-watchdog.vbs every five minutes by default. Installing creates the registrations; the launcher runs at login or through a subsequent watchdog check.
  3. Launcher starts Bun in the background.The VBS launcher uses the checkout as its working directory and runs bun run src/api/server.ts hidden. It tries the WinGet Bun link, then bun.exe on PATH.
  4. Watchdog probes HTTP health.A 200 response from http://127.0.0.1:<port>/health counts as alive. Failure starts another launcher invocation. It does not terminate an old hung process.

These are a Startup script and a Windows scheduled task. There is no Windows Service Control Manager service. The registration references the checkout by absolute path; moving it requires reinstalling the registration. Uninstalling leaves stored data and any already-running API process in place.

Two port variables in the Windows path. The API reads PORT. The watchdog reads HUMEMORY_PORT. Set both consistently when changing the port. Windows launcher logs are under <checkout>/data/logs/, even when the database uses an OS data directory.

Client registration and attribution

The project ships .mcp.json for Claude Code. pnpm cli sources setup merges server registration into detected supported client configurations. Give every client its own HUMEMORY_AGENT, for example claude, codex, kimi or opencode. Separate MCP processes share one store when they resolve the same database path.

The Claude Stop and SessionStart scripts must also be registered in the client's hook configuration. A Git post-commit hook must be installed in each project that should close loops; that hook uses HUMEMORY_HOME to find the humemory checkout. MCP registration does not itself create a transcript hook.

SQLite and vectors are not alternative storage levels. This implementation uses one SQLite database. Vectors are rows in memory_embeddings. Similarity is calculated in JavaScript over stored vectors; there is no separate vector database or ANN service.

Store initialization and concurrency

  1. Open and initialize.new SQLiteStore(path) creates the directory, opens Bun SQLite, sets WAL, a 5-second busy timeout, synchronous=NORMAL, foreign keys and a 16 MB cache budget.
  2. Apply schema changes.initSchema() creates or migrates tables. Some script-era changes rebuild a table by creating a replacement, copying data, dropping and renaming.
  3. Build the local search index.loadIntoMemory() loads the memory corpus into a Map and FlexSearch. Each process has its own copy. Search checks SQLite PRAGMA data_version and reloads after another connection changes the database.
  4. Serialize writes.An in-process promise queue and cross-process advisory lock protect store writes. WAL supports concurrent readers; coordination does not turn multi-operation workflows into a single transaction.

Opening many short-lived stores rebuilds the full lexical index repeatedly. Semantic similarity also scans vectors in process memory. Those are concrete corpus-size costs to account for; the scale benchmark is scripts/bench-scale.ts.

05 / Input pipeline

Session → queue → extracted memories

Stop-hook work is deliberately short. It queues a raw session; extraction is performed later. Codex, Kimi and OpenCode imports feed the same durable queue from their supported local session formats.

  1. Capture or discover input.scripts/hook-session.ts receives the Claude Stop event and enqueues the session. A maintenance pass also discovers recent Codex/Kimi/OpenCode sessions unless the corresponding import is skipped.
  2. Deduplicate the queue slot.enqueueMaintenanceSession() hashes source + session ID. A newer transcript for the same session updates its pending slot. Raw transcript data stays in the queue file until successful processing or dead-letter handling.
  3. Acquire queue ownership and claim a job.drainMaintenanceQueue() takes .worker-lock, recovers abandoned processing files and claims a pending file by rename. A pass handles at most the configured batch.
  4. Parse and scope the session.processSession() uses the stored checkpoint's messagesSeen. Parser/import modules normalize each client's transcript; extraction focuses on messages not already covered by the checkpoint.
  5. Prepare a deterministic result, then optionally use a provider.The worker computes rule-based learnings first. If a configured client exists, it attempts LLM extraction under the deadline. The default per-job learning limit is five.
  6. Write each extracted learning.SQLiteStore.add() receives content, keywords, L3 keywords, memory type, directory, session ID, occurrence time, source and agent. The worker does not pass autoGenerate; it does not automatically generate L1 and L2.
  7. Checkpoint and finish.After successful job processing, the queue stores the processed message count and removes the completed claim. The opened store is closed. On failure, retry classification decides whether to retain, retry or park the job.
  8. Record pass health.runMaintenancePass() persists summary counts and duration in maintenance-state.json, then returns. A standalone process ends; the API loop waits for its next interval.
What this pass does not do. Ingestion does not run decay, vector backfill or the dreamer. New rows start at L0, including backdated imported rows; a later decay pass recomputes their age-based state. Checkpoint storage and individual memory writes are separate operations, so this pipeline should not be described as an exactly-once transaction.

Two ways to run the same maintenance operation

pnpm maintenance
pnpm cli maintenance run --skip-imports
pnpm cli maintenance run --skip-codex --skip-kimi --skip-opencode
pnpm cli maintenance status

The API interval prevents overlapping passes within that loop. Queue ownership also prevents two drainers from consuming the same job simultaneously. Import discovery defaults to the last day; it is not an unrestricted replay of every historical session.

06 / Query paths

Lexical search, semantic search and explicit recall

Ordinary search: no LLM

  1. Receive a query.CLI search, HTTP GET /search?q=… and MCP humemory_search call the lexical store search path.
  2. Refresh the index if needed.The store checks for writes from another SQLite connection before using its process-local FlexSearch index.
  3. Search fields in order.InverseSearchEngine tries L3 keywords → L2 essential text → L1 summary → original content. maxLevel limits indexed fields, not the memory's current age state.
  4. Rank candidates.Strict matching requires query terms within one indexed field. When no strict result exists anywhere, a partial-match pass produces lower-scored candidates. Ranking uses field depth, recalls, saillance, recency, trust and query filters.
  5. Return results.Search does not call recall() and does not regenerate text. Original content remains searchable even when the memory's stored state is L3.

Semantic CLI search: embeddings + rank fusion

# First backfill the default model's embeddings:
pnpm cli embed backfill --model bge-m3 --dtype q8
pnpm cli search "concurrent database writes" --semantic

# Alternate backfill models exist:
pnpm cli embed backfill --model small
pnpm cli embed backfill --model base
StageImplementation detail
Text to embedL3 keywords first, followed by original content. The input is not selected solely from currentLevel.
EmbeddingTransformers feature-extraction pipeline, mean pooling, normalization and ONNX quantization. Default bge-m3 q8 has 1,024 dimensions; e5-small has 384, e5-base 768. E5 adds query/passage prefixes.
StorageFloat32 BLOB in SQLite, tagged with the model ID. CLI backfill defaults to a 500-row limit and embedding batches of 32.
QueryThe semantic CLI constructs the default bge-m3 embedder. The search command has no matching --model switch; alternate-model backfill alone does not change its query model.
Candidate lanesLexical candidates and cosine-ranked vectors are collected at up to three times the requested result limit.
Fusionhybrid.ts sums reciprocal ranks with RRF_K = 60, then sorts. Directory filtering occurs after the fused limit and can underfill results.
Missing vectors / load errorsNo vectors for the requested model → lexical results without model loading. With matching vectors present, model-loading failure propagates; it is not a universal silent fallback.

HTTP /search and the current MCP search tool expose lexical search. The semantic path is surfaced by CLI --semantic. Vector rows are invalidated by decay state changes and relevant merge/unmerge/delete operations; run backfill again when needed.

Recall is a separate write

recall(id, agent) increments the recall count, sets the last-recall timestamp and sets saillance to 100. It does not immediately rewrite currentLevel. A later decay calculation uses the more recent recall as its age anchor, so an eligible unmerged trace can return to a more detailed state.

Trusted cross-agent reuse can earn reused verification. A self-declared HTTP agent header is not treated as equivalent to a trusted client identity.

07 / State and representation

Derived text levels and age-based decay

Two distinct concepts share the level names: text representations stored on a row, and currentLevel, the row's age-based state. A decay pass updates state and saillance; it does not progressively destroy the original content or call a summarization model.

LevelRepresentationAge calculation
L0content: original textEffective age below 24 hours.
L1level1Summary: optional summaryFrom 24 effective hours.
L2level2Essential: optional essential textFrom 168 effective hours (7 days).
L3level3Keywords: optional keywordsFrom 720 effective hours (30 days); automatic aging stops here.
L4Lost/merged state, linked by mergedIntoId when mergedThe thresholds array contains 2,160 hours, but the age loop checks only L3 through L0. Time alone does not transition a row to L4.

Exact state calculation

if photographic: level = 0 else if already L4 or merged: level = 4 else: effectiveAge = min(age since creation, age since last recall) slowdown = min( (1 + recallCount × 0.3) × (saillance ≥ 70 ? 1.5 : 1) × (verified ? 1.5 : 1), 2.5 ) finalAge = effectiveAge / slowdown level = highest matching threshold among L0…L3

decayRate is calculated and persisted, but the current level calculation does not use it. Content length and keyword count are not additional level slowdown factors in this implementation. The 2.5× cap applies to the product of all level slowdown factors.

When derived text is generated

generateMemoryLevels() is called when an add requests autoGenerate, and by relevant automatic merge operations. Without an injected LLM, whitespace is compacted, L1 is truncated to 300 characters, L2 to 100 characters, and L3 is a capped list of unique words. CLI encode --auto enables this generation path; it does not automatically install the maintenance LLM client.

pnpm cli encode "A reusable technical learning" --auto
pnpm consolidate
# HTTP: POST /decay

SQLiteStore.updateDecay() writes current_level and saillance and invalidates changed-level vectors. The consolidate script also handles script disuse. decayCycleHours: 24 is an algorithm constant, not an automatically installed scheduler. Configure a scheduler explicitly for repeated consolidation.

08 / Event and time execution

Intentions, cues, scripts and SessionStart

An intention is a future task. A script is an ordered procedure. A cue is a trigger targeting either one. These are separate tables and lifecycles; intentions and scripts are not retrospective MemoryType values.

Intention lifecycle

add → armed (saillance 100, no decay) trigger → fired (saillance loses 10 per elapsed day, floor 0) explicit close → closed (saillance 0, cues cancelled) expiry of eligible armed intention → expired (saillance 0)

A commit closes a loop only through an explicit Closes loop-<id> marker. File-overlap scoring can suggest related loops; it never closes them. commit-closer.ts owns this behavior.

Trigger behavior and recurrence

CueInputWhen it fires / what repeats
ISO timestamptime:<ISO timestamp>Time resolver fires when due. One-shot cue becomes fired.
Croncron:0 9 * * 1Resolver checks due occurrences since the last firing or arming, with catch-up bounded to seven days. Cron uses local time. Cue is rearmed after firing; repeated invocations can fire subsequent occurrences.
File openevent:file_open:src/a.tsRequires an explicit matching event. No automatic filesystem watcher is created. One-shot cue becomes fired.
Branch switchevent:branch_switch:mainMatching event; SessionStart also uses the current Git branch in its script context path. One-shot cue becomes fired.
Error patternevent:error_pattern:<pattern>Requires a submitted matching event. No background stderr watcher.

Time triggers run when the resolver is invoked, such as at SessionStart, through CLI resolve or HTTP resolve. A cron specification does not create its own OS cron job. The API maintenance interval imports and extracts sessions; it is not the cue scheduler.

Script lifecycle and execution meaning

human authoring → active agent/API or approved script_candidate → draft → human activate → active active + matching cue → context block with ordered steps disuse or contradiction → archived On firing: fire_count += 1; last_fired_at = now; saillance += 5 (cap 100)

“Run a script” means render its steps into the AI client's context. humemory does not execute shell commands from those steps. Draft and archived scripts do not fire. A non-cron cue is consumed even though the script remains active; recurrence needs a cron cue or deliberate rearming/new cues.

Unpinned active scripts get a 60-day disuse grace period, then lose 10 saillance per month of disuse. Below 20, consolidation archives the script and writes a script_archived notice. Firing resets the disuse anchor. A winning contradiction against a script archives it immediately. Revoking the contradiction restores active status but leaves its cues cancelled.

SessionStart, from invocation to output

  1. Collect context.hook-session-start.ts obtains the project working directory and current Git branch, then calls buildSessionContext().
  2. Resolve due cues.The context builder resolves time cues and its supported context events. This can change intention/cue state or mark a script as fired. Resolving time cues can affect targets outside the currently rendered project.
  3. Select local context.It collects relevant open loops, eligible traces and one script at most. Trace selection includes L2/L3 state and a saillance threshold of 60; script ties use effective saillance including disuse.
  4. Render bounded Markdown.Sections contain loop identifiers, trace excerpts and up to eight rendered script steps. The default item budget is ten per section. Budgets and sanitization limit output size. Non-human or insufficiently verified data is wrapped in <humemory-untrusted>.
  5. Emit on stdout and exit.The AI client receives the block through its hook mechanism. This operation does not perform a decay sweep, a generative LLM call or automatic trace recall.

pnpm cli intent resolve
pnpm cli intent close <intention-id>
pnpm cli script list

09 / Cross-session batch

Dreamer: collection, clustering, proposals and review

The dreamer is an explicit batch function, runDreamer(). It has a start, a bounded collection phase, a proposal phase and a returned report. It does not run continuously. The current CLI and HTTP paths do not configure a generative model for it.

pnpm cli dream run
pnpm cli dream run --window 30 --clusterer vector
pnpm cli dream review
pnpm cli dream approve <proposal-id>
pnpm cli dream reject <proposal-id>
  1. Start and expire old proposals.The CLI constructs a store and selects the keyword clusterer by default. runDreamer() expires pending proposals past their TTL.
  2. Collect a bounded memory set.It reads up to 500 memories and applies the default 30-day creation window. L4, merged memories and active contradiction losers are excluded from the clustering set.
  3. Cluster.Keyword mode uses Jaccard similarity with threshold 0.34. Vector mode obtains embeddings for its model, computes missing ones and builds cosine-based connected components. Default bge-m3 clustering threshold is 0.740; e5-small is 0.855 and e5-base 0.825.
  4. Qualify recurrence.A cluster qualifies with at least three traces from two sessions, or at least two distinct agents. Confidence uses base provenance trust, without feeding existing verification bonuses back into clustering.
  5. Apply the corroboration rule separately.Keyword recurrence can earn verification when it also spans two agents, two sessions and two directories. The vector path additionally has a 0.99 similarity guard, documented in code as the disabled-auto-corroboration sentinel.
  6. File semantic proposals.Qualifying clusters produce promote_semantic proposals. A hash of kind + sorted member IDs prevents duplicate filing. Normal proposals expire after 14 days.
  7. Mine other current proposal paths.Eligible armed/fired loops open for at least 30 days can yield close_stale_loop. At least two correction-winning memories in one directory can yield script_candidate, with up to six ordered steps (200 characters each), using L2 essential text or original content, and no LLM.
  8. Return and end.The report includes considered memories, clusters, filed/expired proposals, stale loops, corroborations and script candidates. The command ends. Approval or rejection is a later, separate operation.
Proposal generation and approval are different. Running the dreamer normally creates review rows. It can also write corroboration metadata during the run; it does not require proposal approval for that metadata rule. CLI/HTTP approval applies proposal effects and then marks the proposal approved as separate operations.

10 / Evidence and corrections

Trust, provenance and context protection

Saillance controls prominence. Trust scores evidence and source authority separately. A frequently recalled memory is not automatically a human-verified fact.

ComponentCurrent values / rule
Base provenancehuman 60; hook 45; agent 35; llm_generated 25; dream_proposal 20.
Verification bonushuman +25; grounded +20; reused +15; corroborated +8.
Refutation penalty−15 per refutation, capped at three. Final trust score is clamped to 0–100.
Verification evidenceExplicit human verification, grounding in a closed loop, trusted cross-agent reuse or eligible corroboration. A source label alone is not sufficient.
Contradiction against memoryAuthority rules choose the supported winner. Loser saillance is reduced with a floor of 5; active losers stay searchable but are excluded from normal injected context.
Contradiction against scriptArchives the script and cancels its cues. Revocation restores active status but does not rearm cues.
Injected contextLength limits, marker escaping and <humemory-untrusted> boundaries distinguish stored suggestions from trusted instructions. Human-authored scripts can render bare.
Merge reversibilityDerived-level revisions are captured before overwrite; unmerge restores the previous representation. Original trace content remains a separate stored field.

Maintenance retries preserve sessions during outages

  1. Classify the failure.Database-open/locked errors, disk-full, read-only filesystem and non-constraint SQLite failures are infrastructure failures. They do not spend the job's retry budget.
  2. Stop an outage-shaped pass.A circuit breaker aborts after three consecutive failures by default. Untouched jobs are not claimed.
  3. Finalize retry accounting.If an aborted pass processed zero jobs, retries charged during that pass are refunded. A successful job proves the machine can work and removes that amnesty.
  4. Park exhausted job failures.A genuine job failure can spend five attempts, then retains the transcript in a dead-letter file. Requeue resets attempts without overwriting a newer live job for the same session.
